# Admintz Client Portal — WordPress plugin (MVP)

Реалізація ТЗ "адмінка + клієнтський кабінет" як кастомний WordPress-плагін.

## Продакшн-деплой (поточний стан)

- Сайт: `https://optordashboard.space` (і `www.`), self-managed VPS (173.242.54.204,
  Ubuntu 24.04, 1 CPU / 1.9GB RAM + 2GB swap).
- Стек: nginx + PHP 8.3-FPM + MariaDB 10.11, SSL через Let's Encrypt (certbot,
  автопродовження).
- WP-Cron вимкнено (`DISABLE_WP_CRON`), реальний system cron б'є `wp-cron.php`
  кожні 5 хв.
- Firewall (ufw): відкрито тільки SSH, 80, 443.

## Бекапи

Щодня о 03:00 сервер сам робить бекап і заливає в Backblaze B2 (бакет
`optordashboard`), нічого локально не лишає. **Процедуру відновлення перевірено
наживо 2026-10-30** — реально розгорнуто з бекапу в ізольовану тестову БД на
цьому ж сервері, всі клієнти й таблиці на місці, дані збігаються.

**Відновити на новому сервері — 5 команд:**

```bash
# 1. На чистому VPS (Ubuntu 24.04) поставити: nginx, php8.3-fpm (+розширення
#    php-mysql php-curl php-gd php-mbstring php-xml php-zip php-intl), mariadb-server,
#    rclone, і прописати /root/.config/rclone/rclone.conf з ключами B2 (див. нижче).

# 2. Скачати останній бекап
rclone copy b2backup:optordashboard/files/ . --include "*" && ls -t files_*.tar.gz | head -1
rclone copy b2backup:optordashboard/db/ .

# 3. Розпакувати сайт
tar xzf files_*.tar.gz -C /var/www/

# 4. Підняти базу
mysql -u root -p -e "CREATE DATABASE wordpress CHARACTER SET utf8mb4;"
gunzip -c db_*.sql.gz | mysql -u root -p wordpress

# 5. Права, nginx-конфіг (копія з цього README), SSL (certbot), DNS A-запис на новий IP
chown -R www-data:www-data /var/www/portal
```

Якщо DB-креденшли на новому сервері інші — поправити `/var/www/portal/wp-config.php`.

Технічні деталі (що саме бекапиться, звідки тягнути ключі, ротація) — у коментарях
скрипта `/root/backup.sh` на сервері та в конфігу `/root/.config/rclone/rclone.conf`.

## Встановлення

1. Скопіювати папку `client-portal` у `wp-content/plugins/`.
2. Активувати плагін у wp-admin → Плагіни. При активації створюються таблиці
   `wp_cp_clients`, `wp_cp_links`, `wp_cp_stats`, роль `cp_client` і планується cron-синк.
3. Settings → General → встановити **часовий пояс сайту на Europe/Kyiv** — звіт із
   Keitaro групується по дню саме в цьому часовому поясі (`wp_timezone_string()`).
4. Створити звичайну WP-сторінку (напр. "Кабінет") з шорткодом `[cp_dashboard]`.
5. Admin → Клієнтський портал → Налаштування:
   - вказати ID щойно створеної сторінки (для редіректу клієнта після логіну);
   - вказати Keitaro URL та API Key;
   - натиснути "Перевірити з'єднання з Keitaro".
6. Admin → Клієнтський портал → Додати клієнта — створити логін/пароль (email тут
   потрібен лише технічно для wp_create_user, листи клієнту не надсилаються).
   Пароль (введений або автогенерований) показується **один раз** одразу після
   створення — WordPress зберігає тільки хеш, тож пароль неможливо подивитись
   пізніше. Щоб видати клієнту новий пароль згодом — кнопка "Скинути пароль" у
   списку клієнтів (генерує новий, показує один раз, старий перестає діяти).
7. На сторінці "Прив'язки" (кнопка біля клієнта в списку) додати всі його кампанії
   Keitaro — одному клієнту можна прив'язати скільки завгодно Campaign/Source ID.
8. Натиснути "Синхронізувати зараз", щоб одразу наповнити кеш статистики.

### Надійний cron (рекомендовано)

WP-Cron за замовчуванням спрацьовує тільки на вхідному трафіку, що ненадійно для
регулярного синку. На self-hosted VPS рекомендується:

```php
// wp-config.php
define( 'DISABLE_WP_CRON', true );
```

і системний cron (інтервал синку в налаштуваннях плагіна — 15 хв, тому доцільно
бити частіше, щоб не пропускати тригер):

```
*/5 * * * * curl -s https://SITE/wp-cron.php > /dev/null 2>&1
```

## Архітектура (короткий опис)

- **Auth**: WP login/logout, без email password recovery (рішення: email не
  потрібен, логін/пароль видає і зберігає тільки адмін; самостійне відновлення
  паролю для ролі `cp_client` вимкнено навмисно — див. `CP_Dashboard::disable_self_service_reset`).
  2 ролі — `administrator` (повний доступ) і `cp_client` (тільки свій кабінет,
  доступ у wp-admin заблоковано).
- **Admin panel**: `wp-admin` → CRUD клієнтів, прив'язка до **кількох** Keitaro
  кампаній на клієнта (сторінка "Прив'язки"), налаштування API.
- **Keitaro integration**: `CP_Keitaro_Api` — HTTP-клієнт до Keitaro Admin API.
  Cron-джоба (`CP_Sync`) раз на N хвилин тягне звіт по кожній Client→Campaign/Source
  прив'язці, **підсумовує всі кампанії клієнта по кожному дню** і кладе в локальну
  таблицю `wp_cp_stats` (upsert по даті). Підсумовування важливе: у клієнта може
  бути кілька кампаній, і без нього дані однієї кампанії перезаписували б іншу.
- **Client dashboard**: шорткод `[cp_dashboard]` + REST-ендпоінт `GET /wp-json/cp/v1/stats`.
  Дашборд **завжди** читає тільки кеш (`wp_cp_stats`), не Keitaro напряму — тому
  недоступність Keitaro не ламає кабінет клієнта, тільки затримує оновлення даних.
- **Ізоляція даних**: REST-ендпоінт визначає `client_id` виключно з поточного
  залогіненого `wp_user_id` (через `CP_DB::get_client_by_user_id`) — параметр
  `client_id` з запиту ніде не приймається, тож підмінити чужі дані неможливо.

## Статус перевірки Keitaro API (2026-10-29)

Перевірено живим запитом на тестовому інстансі клієнта (`77.91.123.235`, тариф
Advanced):

- ✅ Тариф Advanced **дає** доступ до `/admin_api/v1/campaigns`, `/traffic_sources`
  і `/report/build` з авторизацією через заголовок `Api-Key` — підтверджено
  робочою відповіддю 200 OK, Export/вищий тариф не потрібен.
- ✅ Реальні назви полів звіту (отримані напряму з помилки валідації API, яка
  повертає повний список колонок): `clicks`, `regs`, `leads`, `sales`, `deposits`,
  `revenue`, `sale_revenue`, `reg_revenue`, `deposit_revenue`, `roi`, `profit` та
  інші. Код (`class-cp-keitaro-api.php`) оновлено на `clicks → clicks`,
  `registrations → regs`, `deposits → deposits`, `revenue → revenue`, `roi → roi`.
- ⚠️ **FTD — знайдено корінь проблеми, виправлення на стороні клієнта.**
  Перевірено по реальних `subid` (через `/admin_api/v1/logs/postbacks`, read-only):
  обидва статуси `dep` і `redep` резолвляться в один internal-тип "Deposit", і
  якщо постбек **не містить `tid`** (унікальний id транзакції), Keitaro не
  створює нову конверсію на повторний депозит, а **оновлює** попередню — зі
  статусом (`dep` → `redep`) і сумою (значення **перезаписується, не додається**:
  напр. 2.28 → 2.17, а не 4.45). Тому зараз `deposits`/`revenue` зі звіту не
  відповідають реальній кількості/сумі депозитів при повторних платежах.
  **Рішення (підтверджено клієнтом):** додати `tid` (унікальний id платежу) до
  постбеків з депозитами + перевірити в Keitaro Settings → Типи конверсій, що є
  окремий тип для `redep`. Після цього `FTD = перший 'dep' по subid`,
  `Revenue = сума dep+redep`. **До впровадження `tid` на їхній стороні** FTD у
  коді лишається тимчасово рівним `deposits` (погоджений fallback для MVP) —
  див. `class-cp-keitaro-api.php`. Коли `tid` додадуть — потрібно повторно
  перевірити на реальних даних і, можливо, оновити `map_report_rows()` під нові
  метрики/типи конверсій.
- Тестова кампанія (`campaign_id=18`) має тільки кліки, конверсій 0. Реальні
  кампанії клієнта (`id=15`, `id=16`) мають і кліки, і конверсії — саме на них
  перевірено все вище.

### ROI: обмеження через відсутність cost-даних

Витрати (`{cost}` у постбеку) не завжди передаються в трекер, тож Keitaro не
завжди коректно рахує ROI сам. Рішення (підтверджене клієнтом):

- За замовчуванням дашборд показує `roi`, який повертає сам Keitaro (підсумований
  по всіх кампаніях клієнта за день).
- Додатково на дашборді клієнта є тогл "Внести власні витрати" — клієнт сам вводить
  суму витрат за обраний період, і ROI миттєво перераховується на фронтенді як
  `(Revenue - Cost) / Cost * 100`, без звернення до сервера (це свідомо зроблено
  як легка UI-фіча без нової таблиці/REST-ендпоінта — позначено клієнтом як
  "не принципово", головне щоб працювало просто). Значення не зберігається між
  сесіями/переглядами — це лише разовий перерахунок "на екрані".

## Чек-лист тестування (п.7 ТЗ)

- [ ] Авторизація: логін/пароль, блокування клієнта (блокований клієнт бачить
      повідомлення "заблоковано" і не отримує дані через REST), відсутність
      self-service password reset для ролі `cp_client`.
- [ ] Правильність статистики: порівняти цифри в кабінеті клієнта з тим, що показує
      сам Keitaro за той самий період — окремо для клієнта з 1 кампанією і з
      кількома (перевірити, що підсумок коректний, а не з останньої кампанії).
- [ ] Прив'язка клієнта до кампанії: створити 2 тестових клієнтів з різними
      Campaign/Source ID, перевірити, що кожен бачить лише свої цифри.
- [ ] Ізоляція даних: спроба викликати REST-ендпоінт під одним клієнтом і
      переконатись, що дані іншого клієнта недоступні ні через параметри запиту,
      ні іншим шляхом.
- [ ] Помилки/недоступність Keitaro API: тимчасово зламати API-ключ/URL і
      переконатись, що (а) cron-синк падає в лог, але не ламає сайт, (б) дашборд
      клієнта продовжує показувати останні закешовані дані.

## Відкриті питання, що лишились

1. **FTD/Revenue при повторних депозитах** — чекаємо, поки клієнт додасть `tid`
   до постбеків з депозитами і перевірить типи конверсій у Keitaro (див. розділ
   вище). Без цього `FTD = Deposits` і повторні депозити перезаписують суму
   замість підсумовування.
2. Доступ до самого WP-сайту/хостингу на VPS, щоб поставити плагін і прогнати
   чек-лист на реальних кампаніях (`id=15`/`id=16`).
